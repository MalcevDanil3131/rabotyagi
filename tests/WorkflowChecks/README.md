# Проверка процесса заявок

Консольная интеграционная проверка без дополнительного тестового фреймворка. Использует настоящий PostgreSQL и запускает собранный API на `127.0.0.1:5188`.

`PriceChecks.cs` проверяет согласование стоимости: права, точность суммы, версии,
отказ и повторное предложение, конкурентные решения, серверный запрет старта,
снимки в истории и откат обеих операций при ошибке записи события. Основной
жизненный цикл и переназначение также проходят согласование через API.

`DemoChecks.cs` проверяет ограничения окружения, отдельной БД и локальных запросов
без подключения к PostgreSQL: `dotnet run --project tests/WorkflowChecks -- --demo-guards-only`.
`DemoIntegrationChecks.cs` создаёт дополнительную базу `rabotyagi_demo_checks_<ID>`
на том же выделенном тестовом PostgreSQL и запускает Demo API на `127.0.0.1:5190`.
Проверяет шесть настоящих сессий/ролей, запрет произвольного и внешнего входа,
сохранность изменённых ролей и заявок после перезапуска, фильтрацию до пагинации,
общие счётчики и отказ клиенту. База, файлы и процесс удаляются после проверки.
Production API отдельно проверяется на недоступность демовхода.

`DemoFixtureChecks.cs` проверяет актуальные примеры согласования цены, оба аккаунта
исполнителей, порядок событий до начала работы и решение клиента через обычный API.
Обновление демобазы без маркера версии проверяется со сравнением всех полей старых
заявок, истории и пользователей; повторный запуск не должен добавлять дубликаты.

`ReassignmentChecks.cs` проверяет замену на трёх разрешённых этапах, запрещённые
статусы, права клиента/работника/диспетчера/суперадминистратора, обязательную причину,
недоступного нового работника, сохранность предыдущего отчёта и фото, права прежнего
и нового исполнителей, повтор и устаревшую версию запроса, конкурентную замену и
откат при ошибке записи истории. Новый исполнитель проходит начало работы и новую
отправку отчёта. Все fixtures и ошибки сохранения изолированы в тестовой БД.

`HistoryChecks.cs` дополнительно проверяет весь журнал успешных действий, UTC,
автора, переходы статусов, единственное событие конкурентного назначения,
доступ ролей и отказ посторонним, пустую историю старой заявки, сохранение снимка
имени после блокировки/переименования/удаления. Временный PostgreSQL trigger
намеренно отклоняет вставку события: проверяется откат создания, статуса,
назначения, отчёта с фотографиями и приёмки клиентом. SQL fault injection
разрешён только для базы с префиксом `rabotyagi_checks_`. API перезапускается
на той же временной БД, после чего история сравнивается с исходной.

```sh
dotnet run --project tests/WorkflowChecks
```

Для запуска требуется WORKFLOW_CHECKS_CONNECTION — строка подключения к выделенному тестовому PostgreSQL с правом CREATE DATABASE. Конфигурация приложения не читается. Создаётся rabotyagi_checks_<случайный ID>, только на неё накатываются миграции; после проверки временная база и фото удаляются. API запускается на 127.0.0.1:5188 в Production с BootstrapAdmin выключенным. BootstrapChecks заранее создаёт изолированные fixtures через Identity.

Проверяются вход/выход, роли, отзыв cookie, JSON адреса, очередь и доступ, модерация, слот, конкурентное взятие одним из двух специалистов, начало работы, запрет преждевременного закрытия, multipart-отчёт и фото, неверный формат фото, возврат с комментарием, повторный отчёт, обсуждение, приёмка, закрытие, блокировка и ошибки пароля.

Для ручной проверки: dotnet run --project tests/WorkflowChecks -- --serve. Задайте WORKFLOW_CHECKS_PASSWORD через окружение самостоятельно; без него пароль случайный и не выводится. Администратор: bootstrap@checks.local; клиент: client@checks.local; исполнители: worker1@checks.local и worker2@checks.local; диспетчер: dispatcher@checks.local. Все используют заданный тестовый пароль и существуют только во временной базе. Vite: API_PROXY_TARGET=http://127.0.0.1:5188. Enter завершает сервер и удаляет тестовую базу.

ClientAcceptanceChecks.cs проверяет прямую приёмку клиентом, версии отчётов, права, повторные и конкурентные решения, прежние Approved и атомарный откат при ошибках истории. Подробнее: [приёмка](../../docs/client-acceptance.md).

OrderPaginationChecks.cs проверяет GET /api/order/page на более чем 100 записях
в изолированной демобазе: фильтры до пагинации, literal-поиск, роли, общие счётчики,
пустую и сокращённую последнюю страницу, независимую карточку после изменения
статуса. Подробнее: [список заявок](../../docs/order-list.md).

SecurityChecks.cs создаёт отдельную `rabotyagi_security_checks_<GUID>` и API :5191.
Проверяет лимиты входа/регистрации/смены пароля и общие ограничения чтения/записи,
восстановление после окна, блокировку, cookie, Origin/CORS и откат регистрации.
Отдельный запуск: `dotnet run --project tests/WorkflowChecks -- --security-only`
с WORKFLOW_CHECKS_CONNECTION к выделенному тестовому PostgreSQL. Обычный набор
также запускает эти проверки. Производственные ограничения проверяются здесь;
для массовых бизнес-проверок лимиты повышены только у временного процесса.
[Настройки и ограничения](../../docs/login-security.md).

BackupChecks.cs запускается отдельно через `--backup-only` или `Test-Backups.cmd`.
Требует PowerShell 7, GnuPG из Git for Windows и текущего отдельного PostgreSQL на
127.0.0.1:55439. Создаёт только новые rabotyagi_demo_backupcheck_<GUID> и
rabotyagi_demo_restore_<GUID>, проверяет scripts/DatabaseBackup.psm1, полный цикл
восстановления с фото, идентичность таблиц/индексов/ограничений и API на :5192.
Готовый зашифрованный пример/отчёт сохраняются, свои тестовые БД удаляются.
Обычный WorkflowChecks не делает новые резервные копии автоматически.
[Подробности и ограничения](../../docs/backup-restore.md).

OrderRepairChecks.cs проверяет конкурентное закрытие слота, блокировку и снятие
роли перед первым назначением, отказ удаления заменённого фото после сохранения
отчёта, постоянную очередь повторной очистки, защиту используемых фото и сохранение
исходной ошибки SaveChanges при одновременном отказе очистки. Для воспроизведения
ошибки удаления используется блокировка файла Windows через FileShare.None.
Все заявки, фотографии и изменения пользователей создаются в новой временной
rabotyagi_checks_<GUID>. Реальная демобаза и основная БД для этих проверок не нужны.

Новый контейнерный демостенд проверяется отдельно из корня проекта через
`pwsh -NoProfile -File tests/DockerDemoChecks.ps1 -Rebuild`.
Требуются уже запущенный Start-Demo.cmd стенд на 3001 и PowerShell 7.2+.
Проверяются изоляция портов/volumes, быстрый вход шести ролей, заявки/цены/история/фото,
защита демовхода, готовность API, сохранность данных и cookie после пересоздания
контейнеров. Скрипт обращается только к проекту rabotyagi-demo и не удаляет volumes.

Production-конфигурация проверяется из корня проекта через
`pwsh -NoProfile -File tests/ProductionDeploymentChecks.ps1`.
Скрипт собирает production-образы и создаёт новый Docker-проект с отдельной БД.
Проверяет явный шаг миграций, первоначального администратора, проверяемый TLS,
cookie, доверенные прокси, отдельные лимиты клиентов и перезапуск.
Порты 18080/18443 используются только на loopback. Системное хранилище
сертификатов не меняется, тестовый CA доверен только клиенту проверки.
Контейнеры и сети теста удаляются, volumes сохраняются.
[Подготовка выпуска](../../docs/production-release.md).
