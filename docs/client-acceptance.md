# Прямая приёмка работы клиентом

Назначенный исполнитель отправляет отчёт штатным multipart API. Заявка переходит
в `WorkFinished` («Приёмка клиентом»). Только инициатор принимает работу или
возвращает её на доработку с непустым замечанием (до 2000 символов).
Принятие сразу переводит в `Completed`, возврат — в `Rework`. После доработки
исполнитель отправляет новый отчёт, который клиент рассматривает заново.
Решение не выполняет оплату и не создаёт платёжных обязательств в приложении.

`POST /api/order/{id}/review`: обязательные `approved` (boolean), `expectedUpdated`
(точная строка `updated` из DTO), необязательное `feedback` (обязательно для отказа).
Это изменение контракта прежнего endpoint проверки диспетчером: фронтенд и API
нужно обновлять вместе. Сотрудники и назначенный исполнитель получают 403,
посторонний пользователь — 404, анонимный — 401. Владение заявкой проверяется
по InitiatorId, независимо от роли пользователя.

Устаревшая версия, повтор решения, неподходящий статус или отсутствие отправленного
отчёта дают 409. Неполное решение и пустое замечание при возврате дают 400.
Кнопки блокируются при сохранении; успех обновляет список, карточку и историю.
Ошибка остаётся в карточке, замечание не теряется; для 409 нужно обновить данные.
При переключении заявок карточка создаётся заново и формы не переносятся.

События `WorkAcceptedByClient` и `WorkReturnedByClient` сохраняют автора, UTC,
снимок имени, переход статуса, замечание и текущую сумму. Один SaveChanges
сохраняет решение и событие атомарно. Concurrency token Updated защищает
одновременные принятие/возврат и изменение отчёта.

Новых таблиц и миграций нет: типы событий хранятся строками в существующем журнале.
Старые события ReportApproved/ReportReturned не изменяются и сохраняют свои подписи.
Существующие `Approved` с отправленным отчётом также доступны владельцу для
прямого завершения или возврата; новые заявки этот промежуточный статус не используют.
Закрытие через общий PATCH статуса сотрудникам больше не разрешено. Существующие
завершённые заявки, суммы и история не переписываются. Старый отчёт без сохранённого
согласования цены может быть принят владельцем; цена задним числом не создаётся.

Демонабор `client-acceptance-v2` добавляется один раз и содержит готовые карточки
«Клиенту: принять работу», «Клиенту: вернуть работу на доработку»,
«Исправить замечания клиента», «Работа принята клиентом». Старые примеры сохраняются.
Проверка: войти клиентом, вернуть второй отчёт с замечанием, переключиться на
исполнителя №2, отправить исправленный отчёт, вернуться клиентом и принять.
Образец фотографии вымышленный. Для повторной отправки можно оставить это фото.

ClientAcceptanceChecks проверяет доступ, версии, обязательность решения/замечаний,
допустимые статусы, старые Approved, конкурентные решения и откат при ошибках истории.
Основной WorkflowChecks проходит возврат, повторную отправку и завершение через API,
а также сравнивает историю после перезапуска. Тесты используют только временные БД.
