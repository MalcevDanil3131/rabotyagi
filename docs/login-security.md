# Защита входа и ограничение запросов

Вход использует Identity PasswordSignInAsync с lockoutOnFailure=true.
По умолчанию 5 неверных паролей временно запрещают вход на 15 минут.
AccessFailedCount и LockoutEnd сохраняются в существующей таблице AspNetUsers;
перезапуск API их не сбрасывает. Успешный вход сбрасывает счётчик ошибок.
Автоматическая блокировка запрещает новые входы; действующие сессии не отзываются
из-за чужих неудачных попыток. Административная блокировка, как и раньше, меняет
security stamp и отзывает сессии. Если LockoutEnabled ранее явно выключили,
Identity не включает его задним числом; IP-лимит продолжает действовать.

Неизвестный email, неверный пароль и заблокированный аккаунт возвращают одинаковые
400 и русское сообщение, без выдачи cookie. Для неизвестных и заблокированных
пользователей дополнительно выполняется проверка случайного dummy-хеша для
уменьшения простых различий времени ответа. Это не гарантия идентичного времени
и не полное устранение возможности определить email через регистрацию.

Новые и изменяемые пароли: 10–128 символов, заглавная/строчная буквы, цифра и
спецсимвол (стандартные требования Identity). Правила не меняют существующие
пароли и не препятствуют проверке старого корректного хеша. Пароли не выводятся
в логи и примеры. Вход ограничивает пароль 1024 символами, email — 254.
DTO ограничивают размеры прочих полей. Тело входа/смены пароля — до 8 КиБ,
регистрации — до 16 КиБ; oversized запрос получает 413. Создание пользователя
и назначение роли User находятся в одной транзакции; cookie выдаётся после commit.
Ошибка роли не оставляет частично созданный аккаунт. Смена пароля обновляет
security stamp внутри Identity, отзывает старые cookie и обновляет текущую сессию.

## Лимиты по умолчанию

| Запросы одного IP | Допуск | Окно |
| --- | --- | --- |
| Чтение `/api` (GET/HEAD) | 600 | 60 сек. |
| Изменения `/api` (остальные методы) | 120 | 60 сек. |
| POST `/api/account/login` | 10 | 60 сек. |
| POST `/api/account/register` | 5 | 600 сек. |
| PATCH `/api/account/password` | 5 | 600 сек. |
| POST `/api/demo/login/{key}` | 30 | 60 сек. |

Общие и отдельные лимиты суммируются как ограничения: запрос должен пройти оба.
Учитываются успешные, неуспешные и невалидные попытки; смена email не даёт новый
IP-бюджет. FixedWindow ASP.NET Core работает без очереди. Лимитер стоит после
routing/CORS, перед аутентификацией: лишние запросы не проверяют cookie в БД.
Ответ 429 содержит JSON error/retryAfterSeconds и Retry-After в секундах,
Cache-Control: no-store. CORS разрешает фронтенду прочитать Retry-After.
Автоматических повторов мутаций нет. Фронтенд сохраняет статус/ожидание в ApiError,
показывает таймер и блокирует кнопки входа, регистрации, смены пароля и демовхода
до указанного времени. Закрытие формы не обходит серверный лимит.

Все параметры находятся в секции `RequestSecurity` и поддерживают env-переменные:
`ReadPermitLimit`, `WritePermitLimit`, `ApiWindowSeconds`, `LoginPermitLimit`,
`LoginWindowSeconds`, `RegisterPermitLimit`, `RegisterWindowSeconds`,
`PasswordPermitLimit`, `PasswordWindowSeconds`, `DemoPermitLimit`,
`DemoWindowSeconds`, `FailedLoginLimit`, `LockoutSeconds`.
Например, `RequestSecurity__LoginPermitLimit=10`. Нулевые/отрицательные и чрезмерные
значения отклоняются при старте до подключения к БД. Лимиты намеренно не отключаются
в деморежиме. Изолированные тесты используют меньшие окна для проверки восстановления;
массовый WorkflowChecks повышает общий лимит только своего временного API.

Лимиты находятся в памяти одного процесса и обнуляются при его перезапуске.
Для нескольких реплик понадобится общий ограничитель или лимиты на шлюзе.
Ключ — фактический RemoteIpAddress соединения, а не email или входящий
X-Forwarded-For/X-Real-IP. Поддельные заголовки не меняют бюджет. При текущем Vite/
nginx-прокси пользователи делят IP прокси, как и пользователи одного NAT. При
подготовке публичного развёртывания нужно настроить доверенные прокси/реальные IP
или ограничения на шлюзе. Нельзя включать доверие произвольному X-Forwarded-For.
Ограничитель запросов не заменяет сетевую защиту от DDoS.

## Браузер, cookie и Production

Cookie явно HttpOnly, SameSite=Lax. В Production по умолчанию Secure; нужен HTTPS.
В Development/Demo HTTP на loopback сохраняется. `RequestSecurity__RequireHttpsCookies=false`
используется только изолированным тестовым API на loopback. На публичном сайте
Secure следует сохранить. Основной HTTP Compose в рамках этой задачи не обновлялся
и не запускался: перед применением этой версии к нему нужно подготовить HTTPS.

Substring-проверка origin.Contains("localhost") удалена. В Development/Demo
разрешены точные http://localhost и http://127.0.0.1 на портах 5173/3000.
В Production список внешних origins по умолчанию пуст; same-origin работает.
Для отдельного фронтенда/TLS-прокси задайте, например,
`RequestSecurity__AllowedOrigins__0=https://<FRONTEND_HOST>` и замените placeholder
реальным origin. Указываются схема, имя и порт без пути/завершающего слеша, без `*`.
За TLS-прокси нужно также разрешить внешний origin, пока upstream видит HTTP.

Изменяющие запросы с чужим/null Origin получают 403; запросы с Sec-Fetch-Site:
cross-site без Origin тоже запрещены. Same-origin и явно разрешённые origins
работают. Небраузерные клиенты без этих заголовков поддерживаются. Это проверка
происхождения браузерных запросов вместе с SameSite, не внедрение token-antiforgery.
Демо-endpoints сохраняют собственные проверки Host/Origin/заголовка и ответ 404;
для них по-прежнему необходим локальный Demo environment и отдельная БД.
Все API-ответы получают no-store и nosniff. Swagger/OpenAPI доступны только
Development/Demo, в Production — 404.

## Проверки и файлы

`SecurityChecks.cs` создаёт только новую БД `rabotyagi_security_checks_<GUID>` на
явно выбранном тестовом PostgreSQL; запускает Production API на loopback:5191.
Проверяет блокировку, единый ответ, восстановление, лимиты/Retry-After, поддельный
IP, CORS/Origin, cookie, смену пароля/отзыв сессии, rollback роли, размер тела,
регистрацию и сохранение блокировки после рестарта. База/процесс/файлы удаляются
после теста. `--security-only` запускает этот набор без бизнес-сценариев; обычный
WorkflowChecks запускает оба. DemoIntegrationChecks дополнительно проверяет лимит
демопереключения и сохранение текущей сессии при отказе. Фронтенд проверяет 429,
разбор Retry-After и отсутствие автоповтора входа/смены пароля.

Новых миграций нет, существующие заявки/события/аккаунты при старте не меняются.
Пароли учебных аккаунтов не добавляются: для демо остаётся быстрый вход. Реальное
проверочное ограничение логина можно увидеть в Network: после 10 попыток с одним
IP в текущем окне следующий POST login даёт 429 с Retry-After. Используйте только
несуществующий учебный email, чтобы не заблокировать нужного пользователя. Проверки
блокировки реального тестового аккаунта уже выполнены во временной БД, а не на
сохранённых демоаккаунтах.
