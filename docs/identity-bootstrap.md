# Первоначальная настройка Identity

Обычный запуск создаёт только отсутствующие роли. Он не создаёт демонстрационные
аккаунты и не меняет существующих пользователей ни в Development, ни в Production.
Новых миграций для этого изменения нет. Program.cs по-прежнему применяет имеющиеся
миграции при старте: не запускайте приложение на рабочей БД без согласования.

## Создание первого администратора

По умолчанию `BootstrapAdmin:Enabled` выключен. Для однократного создания нового
SuperAdmin передайте процессу настройки через защищённую конфигурацию/окружение:

```text
BootstrapAdmin__Enabled=true
BootstrapAdmin__Email=<NEW_ADMIN_EMAIL>
BootstrapAdmin__Password=<UNIQUE_STRONG_PASSWORD>
```

Для Compose им соответствуют `BOOTSTRAP_ADMIN_ENABLED`, `BOOTSTRAP_ADMIN_EMAIL`,
`BOOTSTRAP_ADMIN_PASSWORD`. Значения должны быть доступны окружению Compose;
не добавляйте реальные секреты в Git, команды с сохраняемой историей или логи.
Пароль проверяется штатной политикой Identity. Пользователь и назначение роли
сохраняются одной транзакцией.

После успешного создания выключите флаг (`false`) и уберите email/пароль из
конфигурации и окружения следующего запуска. При выключенном флаге повторный
запуск сохраняет пароли, роли, блокировки и security stamps без изменений.

Если email или имя входа уже существует, bootstrap останавливает запуск с
ошибкой и не меняет аккаунт, даже если тот уже SuperAdmin. Это также происходит
при повторном запуске с забытым включённым флагом. Выключите bootstrap после
успешного создания. Для занятого клиентом email нельзя автоматически повысить
права: используйте другой новый email или действующий интерфейс управления ролями
под уже авторизованным суперадминистратором.

## Старые служебные аккаунты

Обновление кода само по себе НЕ устраняет известные пароли ранее созданных
`user@mail.ru`, `worker@mail.ru`, `dispatcher@mail.ru`, `admin@mail.ru`,
`superadmin@mail.ru`. До публичного запуска владелец должен проверить их назначение,
сменить пароли сохраняемых аккаунтов на уникальные и отозвать прежние сессии;
ненужные аккаунты заблокировать через штатное управление пользователями.
Сначала обеспечьте доступ через безопасный административный аккаунт.
Не удаляйте пользователей напрямую: существующие связи заявок имеют каскады
и ограничения удаления. Автоматическая очистка пользователей этим изменением
не выполняется.

## Тестирование

Для локального показа есть отдельное окружение Demo с собственной базой и
аккаунтами без паролей: [инструкция деморежима](demo-mode.md). В Development и
Production этот механизм запрещён. Интеграционные fixtures создаются явным
запуском `tests/WorkflowChecks` в новой базе `rabotyagi_checks_<ID>`.
Стенд не использует рабочий appsettings.json и требует `WORKFLOW_CHECKS_CONNECTION`
к выделенному тестовому PostgreSQL. Пароли генерируются заново и не печатаются;
для ручного режима можно передать собственный `WORKFLOW_CHECKS_PASSWORD`.

BootstrapChecks проверяет выключенную инициализацию, повторное создание ролей,
успешное создание администратора, конфликт email, сохранность существующих
аккаунтов и откат пользователя при ошибке сохранения роли. WorkflowChecks
проверяет отсутствие дополнительных аккаунтов при запуске API в Production.
