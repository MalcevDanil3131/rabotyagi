# Резервное копирование и восстановление: изолированный контур

Текущий этап не подключает основную базу. Скрипты принимают только источники
`rabotyagi_demo_*` в проверенном локальном демоконтейнере на 127.0.0.1:55439.
Восстановление разрешено только в **новую** `rabotyagi_demo_restore_<32 hex>`.
Ни основная БД, ни существующая пустая БД не могут быть целью восстановления.
Нет флагов обхода этой проверки, `--clean` или восстановления с исходным именем.
Настройки рабочего подключения и `.env` не используются.

С 12 ноября кнопка Start-Demo.cmd запускает новый Compose-стенд на порту 3001.
Текущие скрипты резервного копирования продолжают использовать прежний отдельный
PostgreSQL на 55439 и `.tools/demo-runtime/`. Новый `rabotyagi_demo_docker`
и его volume с фотографиями этим механизмом пока не копируются.

## Проверка одной кнопкой

Запустите `Test-Backups.cmd` в корне проекта. Docker Desktop и отдельный
демоконтейнер должны уже работать. Нужны .NET 10, PowerShell 7.2+, GnuPG и
подготовленная `.tools/demo-runtime/`. GnuPG автоматически находится в PATH
или в Git for Windows; проверенная версия — 2.4.9. PostgreSQL-утилиты запускаются
из отдельного контейнера PostgreSQL 15, поэтому установка psql на Windows не нужна.

Эквивалент в терминале PowerShell 7:

```powershell
pwsh -NoProfile -File .\scripts\Test-DatabaseBackup.ps1
```

Проверка создаёт новый источник `rabotyagi_demo_backupcheck_<GUID>`, применяет
миграции только к нему и заполняет вымышленными аккаунтами/заявками/фото. Текущая
демобаза не является источником этого теста. Затем создаётся зашифрованный архив,
восстанавливается новый экземпляр, сравниваются все таблицы, миграции, ограничения,
индексы, снимки авторов и суммы. Проверяются пароль/роль, новые идентификаторы
sequence и запись события через API. Отдельный API :5192 запускается только на
восстановленной тестовой БД и проверяет вход, заявки, историю и доступ к фото.
В конце удаляются только созданные этим тестом БД и временные восстановленные
фото/ключи; шифрованный пример и отчёт остаются для просмотра.

Успешный прогон печатает `PASS` и пути:

- `.backups/*.zip.gpg` — зашифрованная копия **вымышленных тестовых данных**;
- `.tools/backup-runtime/checks/<GUID>/result.json` — результаты, SHA-256 архива
  и путь к защищённому файлу тестовой парольной фразы;
- `.tools/demo-runtime/backup-checks.log` — журнал последнего запуска агентом;
  при ручном запуске результаты также видны в консоли.

Отчёт хранит проверенные признаки восстановления, но не пароли и не хеши
паролей пользователей. Тестовая случайная парольная фраза сохранена через Windows
DPAPI в закрытой папке того же прогона; это удобно для повторного восстановления
примера на этом ПК. Этот пример не является резервной копией реальных заявок.

## Ручное создание копии отдельной демобазы

```powershell
# Интерактивный запрос парольной фразы, минимум 20 символов:
pwsh -NoProfile -File .\scripts\Backup-Demo.ps1
```

Скрипт читает имя отдельной демобазы из существующего state.json и включает
фотографии из `rabotyagi/.demo/<имя БД>/uploads`. Сам ничего не запускает:
ни Docker Desktop, ни контейнеры, ни API. Поэтому другие контейнеры с restart
policy не возобновляются из-за резервного копирования.

Для выбора отдельного источника используйте `Backup-Database.ps1`:

```powershell
pwsh -NoProfile -File .\scripts\Backup-Database.ps1 `
  -Database '<DEMO_DATABASE>' -UploadsPath '<ABSOLUTE_UPLOADS_PATH>'
```

Placeholders нужно заменить собственными путями/именем отдельной демобазы.
Без UploadsPath копия с существующими ссылками на фото отклоняется. Явный
`-DatabaseOnly` создаёт только копию БД; в ней останутся ссылки на фотографии,
но файлов не будет, что отмечается в manifest. Для полного восстановления
заявок с отчётами используйте обычный режим с фотографиями.

Каталог назначения по умолчанию `.backups` исключён из Git. Можно передать
`-OutputDirectory` на другом локальном диске: каталог должен быть новым или
ранее созданным этим инструментом (с его marker-файлом). Произвольным существующим
папкам права доступа не меняются. Для каталога копий и временной папки задаётся
DACL с доступом только текущему Windows-пользователю и SYSTEM. Ранее созданные
копии не перезаписываются и автоматически не удаляются.

## Что находится в архиве

`pg_dump --format=custom --no-owner --no-acl` создаёт согласованный логический
снимок одной БД, включая данные Identity и историю миграций. Пользователи/роли
Identity — таблицы приложения и входят в копию. Серверные роли PostgreSQL,
tablespaces, конфигурация сервера и WAL в неё не входят. Подробнее:
[официальная документация pg_dump](https://www.postgresql.org/docs/15/app-pgdump.html).

В шифрованном ZIP находятся database.dump, manifest.json и только фотографии,
на которые ссылается БД. Manifest содержит SHA-256 дампа и каждого файла,
версию формата, версию pg_dump, исходное имя БД и время UTC. Состояние ссылок
на фото сравнивается до/после копирования: если оно изменилось, законченная
копия не публикуется. Приложение использует новые GUID для загружаемых файлов,
не перезаписывая старые. При внешнем изменении файлов/обслуживании БД следует
приостановить запись на время копирования. Обычные изменения других таблиц
попадают в согласованный снимок самого pg_dump.

Архив шифруется штатным GnuPG AES-256 с контролем целостности OpenPGP, без
собственной реализации криптографии. Парольная фраза передаётся через stdin,
не аргументы командной строки, переменные окружения или plaintext-файл.
Используются отдельный временный GPG home, `--no-symkey-cache` и фиксированная
S2K-настройка; фоновый gpg-agent не запускается. См.
[официальные параметры GnuPG](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Esoteric-Options.html).

Во время работы **есть временный открытый дамп/ZIP** в закрытом NTFS-каталоге
`.tools/backup-runtime/staging/<GUID>`. Они удаляются при обычном успехе и
обрабатываемой ошибке. После отключения питания/принудительного завершения
могут остаться: перед реальным использованием каталог должен быть на защищённом
диске (например, BitLocker), а остатки нужно проверить и убрать после выяснения
причины сбоя. Шифрование диска этим инструментом не включается. Git и PowerShell
не используются как текстовый канал для бинарного дампа.

## Восстановление

```powershell
$target = 'rabotyagi_demo_restore_' + [guid]::NewGuid().ToString('N')
pwsh -NoProfile -File .\scripts\Restore-Database.ps1 `
  -BackupPath '<ABSOLUTE_BACKUP_PATH.zip.gpg>' -Database $target
```

Будет запрошена та же парольная фраза. Скрипт сначала проверяет отсутствие цели,
полностью расшифровывает и проверяет архив, имена файлов и SHA-256. Неверный
пароль, повреждение или неподдерживаемый пакет не создают БД. Затем createdb
создаёт новый экземпляр, а pg_restore выполняется с `--single-transaction`,
`--exit-on-error`, без `--create`, `--clean`, исходных владельцев/ACL/tablespaces.
При SQL-ошибке изменения откатываются: может остаться новая пустая БД, но ни одна
существующая БД не очищается. Подробности:
[официальная документация pg_restore](https://www.postgresql.org/docs/15/app-pgrestore.html).

Фотографии помещаются в новый `rabotyagi/.demo/<целевая БД>/uploads`; уже
существующая папка назначения тоже запрещена. Сам скрипт не запускает приложение
и не применяет миграции. Ключи Data Protection намеренно не копируются: после
восстановления нужны новые сессии входа. Пароли и роли пользователей сохраняются.
Перед подключением приложения сверьте версию его кода с миграциями из копии:
обычный API при старте автоматически применяет миграции, это отдельное действие.

Восстанавливайте только собственные доверенные архивы: SQL внутри PostgreSQL
dump исполняется при восстановлении. Шифрование не превращает чужой dump в
безопасный код. Секрет парольной фразы должен храниться отдельно от копий,
желательно в менеджере паролей; файл DPAPI от старого ПК его не заменяет.

## Подготовленное ежедневное расписание (ещё не включено)

Для текущего Windows-пользователя можно сохранить парольную фразу:

```powershell
pwsh -NoProfile -File .\scripts\Initialize-BackupPassphrase.ps1
```

Она запрашивается дважды и сохраняется в `.tools/backup-runtime/passphrase.xml`
с DPAPI CurrentUser. Файл не перезаписывается. Для восстановления на другом ПК
нужна исходная парольная фраза из отдельного надёжного хранилища.

Сначала проверьте запланированное действие без создания задачи:

```powershell
pwsh -NoProfile -File .\scripts\Register-DemoBackupTask.ps1 -At '03:00' -WhatIf
```

Убрав WhatIf, владелец регистрирует `RabotyagiDemoBackup` только для отдельной
демобазы. Задача запускает Backup-Demo.ps1, не основной Compose, не Docker и не
API. Время — локальное время Windows. RunLevel Limited, только сессия текущего
вошедшего пользователя, StartWhenAvailable, одновременные запуски игнорируются.
Существующая задача с этим именем не заменяется. Задача не сработает без доступного
Docker и входа пользователя; это удобство локального стенда, не production-служба.
Последний результат Backup-Demo.ps1 хранится в `.tools/backup-runtime/last-run.json`.
Ошибки нужно отслеживать; факт создания задания не доказывает наличие свежей копии.

**В этой работе задача Windows не регистрировалась.** Для основной БД отдельное
расписание/профиль не включены. Перед публичным запуском отдельно потребуются
разрешение владельца, защищённое внешнее хранилище (не тот же диск/volume),
согласованная ротация/сроки хранения, мониторинг ошибок и регулярные учебные
восстановления. Логические копии не дают point-in-time recovery; если нужна
меньшая потеря данных, потребуется настроить WAL/PITR. Копии здесь не удаляются
автоматически: нужно следить за свободным местом.

## Проверки и изменённые файлы

Проверены успешное восстановление, все таблицы/индексы/ограничения, авторизация,
история, суммы, фото, sequence, запись после восстановления, неизменность исходного
содержимого. Также проверены запрет основной/существующей цели, ошибочный пароль,
порча шифротекста, отсутствие фото и SQL-ошибка в середине pg_restore. При последней
проверяется отсутствие частично восстановленных таблиц. Временные файлы после
успеха и ошибок не остаются в staging.

- Новые скрипты: `scripts/DatabaseBackup.psm1`, `Backup-Database.ps1`,
  `Restore-Database.ps1`, `Backup-Demo.ps1`, `Initialize-BackupPassphrase.ps1`,
  `Register-DemoBackupTask.ps1`, `Test-DatabaseBackup.ps1`.
- Кнопка: `Test-Backups.cmd`.
- Проверки: `tests/DatabaseBackupChecks.ps1`, `tests/WorkflowChecks/BackupChecks.cs`;
  новый режим `--backup-only` в `tests/WorkflowChecks/Program.cs`.
- Документация: этот файл, `docs/demo-mode.md`, `tests/WorkflowChecks/README.md`;
  исключения копий в `.gitignore`.

Миграции, приложение, Compose и основная БД не изменяются этой задачей.
