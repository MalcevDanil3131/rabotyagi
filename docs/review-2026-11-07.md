### R1 · P1 для публичного запуска: HTTP Compose и HTTPS-cookie нового API

Для выпуска 12 ноября подготовлен отдельный `compose.production.yaml` с Caddy,

включая независимые лимиты клиентов. Фактическое размещение требует выбора

[Конфигурация и результаты](production-release.md).

**Подтверждено конфигурацией; вход в работающий основной контейнер не проверялся.**

В Compose API работает в Production по HTTP:8080, Nginx слушает HTTP:80.
Новый код по умолчанию создаёт Secure-cookie для Production. Для обычного
публичного HTTP-домена это несовместимый контракт: нужна внешняя HTTPS-точка
входа. Особое поведение localhost нельзя считать проверкой production-развёртывания.

Это не установленная причина сегодняшнего клика в Docker: работающие образы
старше последних изменений, а фактический сбой в интерфейсе Docker не наблюдался.

Ссылки: [compose.yaml:33](/C:/projи/rabotyagi-master/compose.yaml:33),
[nginx.conf:3](/C:/projи/rabotyagi-master/frontend/nginx.conf:3),
[RequestSecurityExtensions.cs:79](/C:/projи/rabotyagi-master/rabotyagi/Core/Extensions/RequestSecurityExtensions.cs:79).

Перед запуском нужны HTTPS, корректный внешний origin и проверка настоящей сессии
через фронтенд. Отключать Secure-cookie на публичном сайте ради HTTP не следует.

### R2 · P1 для развёртывания: лимиты объединяют пользователей за Nginx

**Подтверждено цепочкой конфигурации; нагрузочный тест публичного контура не проводился.**

Nginx передаёт X-Forwarded-For, но приложение не настраивает обработку доверенных
прокси. Лимитер использует RemoteIpAddress соединения. При этой конфигурации
пользователи за одним Nginx попадут в общий бюджет: например, пять попыток
регистрации за десятиминутное окно будут суммарным лимитом клиентов этого прокси.

Игнорирование произвольного X-Forwarded-For сейчас защищает от подмены IP — это
правильное безопасное значение по умолчанию. Для production требуется отдельная
настройка доверенного прокси/шлюза, а не доверие любому заголовку клиента.

### R3 · P2: после отправки отчёта открытая карточка временно остаётся старой

**Подтверждено потоком состояния в коде; ручное воспроизведение в браузере не завершено.**

показывать InProgress/Rework и кнопку заполнения отчёта. Следующий фоновый опрос
или ручное обновление исправляет состояние, но пользователь видит противоречие.

### R4 · P2: первое назначение проверяет доступность исполнителя до UPDATE

**Подтверждено кодом; гонка закрытия слота/блокировки не воспроизводилась отдельным тестом.**

SetExecutor сначала отдельным запросом проверяет слот/роль/блокировку, затем
начинает транзакцию и условно обновляет заявку. В UPDATE нет повторной проверки
доступности пользователя. Если слот закрыли или пользователя заблокировали между
этими операциями, уже устаревшее положительное решение остаётся действующим.

Гонка двух работников за одну заявку защищена корректно. Замечание касается
другого объекта — доступности исполнителя. ReassignExecutor уже включает
eligible.Any в условие изменения и показывает подходящий существующий подход.

Ссылки: [OrderService.cs:94](/C:/projи/rabotyagi-master/rabotyagi/API/Features/Order/OrderService.cs:94),
[OrderService.cs:103](/C:/projи/rabotyagi-master/rabotyagi/API/Features/Order/OrderService.cs:103),
[OrderService.cs:146](/C:/projи/rabotyagi-master/rabotyagi/API/Features/Order/OrderService.cs:146),

### R5 · P2: ошибка удаления старого файла может превратить успешный отчёт в HTTP 500

**Подтверждена ветка кода; отказ файловой системы в этом ревью не инъецировался.**

SubmitReport сначала сохраняет заявку/событие/метаданные и устанавливает saved=true.
Потом finally удаляет заменённые фото через File.Delete. Если удаление бросает
исключение, клиент получает ошибку, хотя транзакция БД уже завершена. При откате
БД ошибка очистки новых файлов также может замаскировать первоначальный сбой.

Ссылки: [OrderService.cs:356](/C:/projи/rabotyagi-master/rabotyagi/API/Features/Order/OrderService.cs:356),
[OrderService.cs:363](/C:/projи/rabotyagi-master/rabotyagi/API/Features/Order/OrderService.cs:363).

Нужно отделить результат сохранения от очистки файлов, фиксировать неудачную
очистку для повторного выполнения и добавить тест отказа файловой системы после commit.

## Что уже сделано надёжно

- Статусы, владение и права проверяются сервером, а не только кнопками React.
- Первичное взятие заявки имеет одного победителя; замена защищена версией.
- Принятие цены/работы не может выполнить сотрудник за клиента.
- Изменения заявки и события истории сохраняются атомарно; ошибки записи
  проверяются реальными PostgreSQL-триггерами во временных БД.
- Список фильтруется до пагинации, возвращает общие счётчики; поздние ответы
  старых запросов не заменяют текущую выдачу.
- Есть Identity-lockout, ограничения запросов, защита происхождения браузерных
  запросов, отзыв старых сессий после смены пароля.
- Учебный демовход отделён окружением/БД/проверками; в Production endpoints скрыты.
- Восстановление зашифрованной тестовой копии с фото проверено на отдельном API.

При этом текущие фронтенд-тесты в основном проверяют HTTP-обёртки, загрузчик и
чистые функции. Они не заменяют тесты смонтированных компонентов/реального браузера.
Отсюда возможность R3 при зелёном наборе проверок.

## Почему сайт справа работает, а Docker выглядит иначе

Открытая вкладка — клиент браузера, она не мешает Docker и не занимает серверный порт.
Проверенное состояние:

| Экземпляр | Фронтенд | API | PostgreSQL |
| --- | --- | --- | --- |
| Текущее демо | Node/Vite на ПК, 127.0.0.1:5173 | dotnet на ПК, 127.0.0.1:5189 | rabotyagi-demo-720e9810, 127.0.0.1:55439 |
| Основной Docker Compose | контейнер frontend, порт 3000 | контейнер rabotyagi, порт 5000 | rabotyagi_db, порт 5432 |

Процессы демо на момент проверки: Node PID 14164 и .NET PID 33276.
Все перечисленные контейнеры были запущены. Основной frontend имел healthy.
Это не доказывает успешный бизнес-сценарий в контейнерах: healthcheck проверяет
статическую /healthz Nginx, а не вход и не готовность БД/API.

Docker-образы frontend/API созданы **17 октября 2026 года**. Они не получают
текущий исходный код автоматически: Dockerfile копирует собранные файлы, а Compose
не монтирует в них текущий src. Поэтому это не тот же экземпляр, что новое демо
на 5173. В текущей конфигурации порты этих двух запусков не конфликтуют.

Если открывать демоконтейнер PostgreSQL или его порт 55439, веб-страницы не будет:
это протокол БД, а не HTTP. Сайт основного контейнера связан с портом 3000,
а актуальное демо запускается через Start-Demo.cmd. Доступность основного сайта
по HTTP и вход в него в этом ревью специально не проверялись, чтобы не обращаться
к рабочей БД. Точная кнопка/ошибка пользователя в Docker не наблюдалась, поэтому
её конкретную причину сверх этого разделения подтвердить нельзя.

Не стоит пересобирать основной Compose только ради проверки: новый API выполняет
Database.Migrate при старте. Такое обновление нужно проводить отдельно после
подготовки копии и разрешения владельца, а не как побочный эффект ревью.

## Основные задачи перед запуском, по порядку

1. **Исправить R3–R5 и закрыть их тестами.** Особенно отправку отчёта и отображение
   результата сразу после сохранения. Для R4 нужен именно конкурентный тест слота.
2. **Сделать полный демостенд в отдельном Compose.** Три сервиса, собственная БД/
   volumes, понятная ссылка и команда обновления. Перенос основного стенда сюда
   не подменяет; при занятых портах нужно останавливать только проверенные демопроцессы.
3. **Пройти весь UI на чистых пользователях.** Регистрация/адрес/создание, публикация,
   выдача Worker, слот, взятие, отказ от цены, новая цена, старт, настоящее фото,
   возврат и повторный отчёт, завершение. Добавить браузерную регрессию, мобильную
   проверку, переключение ролей, потерю сети и 409.
4. **Подготовить production-развёртывание.** HTTPS и origins, доверенные прокси и
   реальные IP, закрытие прямого внешнего доступа к БД/API, readiness API, журнал
   ошибок и контролируемый этап миграций вместо неожиданного обновления при запуске.
5. **Включить реальные резервные копии.** Текущие скрипты намеренно ограничены
   demo/test. Для основной БД нужны отдельное разрешение/профиль, внешнее защищённое
   хранилище, сохранённая отдельно парольная фраза, расписание, ротация, контроль
   ошибок и учебное восстановление. Сейчас готовность механизма не означает, что
   основная БД уже автоматически защищена копиями.
6. **Закрыть вход и поддержку новых пользователей.** Восстановление пароля,
   подтверждение контактов и понятный путь одобрения исполнителя. Ранее созданные
   служебные аккаунты нужно отдельно проверить/обезопасить владельцу: новый сидер
   сам не исправляет старые учётные данные.
7. **Определить операционные правила MVP.** Как оплачивается работа, кто помогает
   при споре и отмене после начала, какие уведомления получают стороны. При расчёте
   вне платформы это нужно обозначить явно, не выдавая Completed за факт оплаты.

Можно отложить полноценный эквайринг при явно выбранной внешней оплате, realtime
вместо polling, сложные курсоры, универсальный аудит, аналитику и архив версий фото.
Не стоит откладывать проверяемое восстановление, права доступа, корректное завершение
работы и понятный способ запуска нужного экземпляра приложения.
