# Выпуск Rabotyagi

## Подготовленная конфигурация

`compose.production.yaml` предназначен для отдельного публичного Linux-сервера.
Используется проект `rabotyagi-production` с собственными volumes. Фронтенд
React и API работают на одном домене. Caddy обслуживает собранный интерфейс,
проксирует `/api` и получает/продлевает HTTPS-сертификат для указанного домена.
Требуются корректные DNS-записи и доступные порты 80 и 443.
[Документация автоматического HTTPS](https://caddyserver.com/docs/automatic-https).

PostgreSQL и API подключены к внутренним сетям Docker. Публичные порты принадлежат
фронтенду. API доверяет заголовкам IP/протокола только от заданного адреса Caddy
`172.29.230.10`. Это позволяет учитывать IP клиента в лимитах запросов и правильно
обрабатывать HTTPS-cookie. Адрес и подсеть задаются через `RABOTYAGI_PROXY_IP`
и `RABOTYAGI_PROXY_SUBNET`, если на сервере уже занята подсеть по умолчанию.
[Документация ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).

Обычный API запускается с `Database__ApplyMigrationsOnStartup=false`. Миграции
выполняет отдельный процесс `migrate`, который завершается после применения схемы.
При наличии неприменённых миграций обычный API сообщает ошибку запуска.
Первый суперадминистратор создаётся отдельным процессом `bootstrap`.

Данные сохраняются в `postgres_data`, фотографии в `report_photos`, ключи сессий
в `identity_keys`. В `caddy_data` хранятся данные сертификатов. Полные имена volumes
содержат префикс проекта. Healthcheck проверяет Caddy и доступность БД через API.

## Первый запуск на новом сервере

Нужны Docker Engine с Compose v2 и домен, направленный на IP сервера.
DNS и доступ к серверу предоставляет владелец. Этот сценарий создаёт новую базу
для выпуска. Перенос существующих пользователей и заявок требует отдельного
согласования с владельцем данных.

1. Разместить исходники проекта на сервере.
2. Скопировать `.env.production.example` в `.env.production` и установить права 600.
3. Заполнить домен, email для сертификатов, уникальную метку версии,
   случайный пароль PostgreSQL и данные первого суперадминистратора.
4. Выполнить команды из корня проекта.

```sh
docker compose --env-file .env.production -f compose.production.yaml build api frontend
docker compose --env-file .env.production -f compose.production.yaml up -d --wait postgres
docker compose --env-file .env.production -f compose.production.yaml run --rm migrate
docker compose --env-file .env.production -f compose.production.yaml run --rm bootstrap
docker compose --env-file .env.production -f compose.production.yaml up -d --wait api frontend
```

Значения паролей вводятся владельцем в защищённый конфигурационный файл.
Строка `SITE_DOMAIN` содержит имя домена без схемы, пути и порта.
Например, для домена `app.example.com` сайт открывается по `https://app.example.com`.
Первый вход выполняется с email и паролем, указанными для bootstrap.
После успешного создания администратора удалить из `.env.production` значения
`BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`. Повторный bootstrap для
того же email завершится явной ошибкой конфликта.

Для проверки после запуска открыть сайт, войти, создать заявку и пройти
согласование цены/отчёт/приёмку. Суперадминистратор назначает роль исполнителя
через управление пользователями. Заявку публикует администратор или суперадминистратор.

## Обновление

Перед изменением схемы сохранить резервную копию базы и фотографий, проверить
доступность восстановления. Указать новую метку `RABOTYAGI_RELEASE` и собрать
новые образы. На время миграции остановить API, выполнить `run --rm migrate`,
затем запустить `up -d --wait api frontend`. Запуск bootstrap при обновлении
обычного экземпляра не требуется.

Откат версии со сменой схемы требует проверки совместимости старого кода
или восстановления копии. План восстановления должен охватывать PostgreSQL,
фотографии и ключи сессий. Существующие скрипты бэкапов в этом репозитории
проверены на изолированном локальном PostgreSQL, их профиль для публичного
сервера и внешнее хранилище предстоит настроить при выборе размещения.

## Проверка конфигурации на этом компьютере

```powershell
pwsh -NoProfile -File .\tests\ProductionDeploymentChecks.ps1
```

Скрипт собирает production-образы и запускает новый проект
`rabotyagi-release-checks-<GUID>` с новой тестовой базой. Проверочные порты
18080 и 18443 привязаны к loopback. Для localhost используется локальный центр
сертификации Caddy, которому доверяет только HTTP-клиент этого теста.
Проверяются явные миграции, bootstrap, HTTPS, cookie, авторизация, защита от
чужого Origin, лимиты и сохранение сессии после перезапуска API.
После проверки удаляются контейнеры и сети этого запуска. Volumes сохраняются.
Результаты находятся в `.tools/release-checks/`.

Проверка 12 ноября 2026 года завершилась успешно — 30 проверок production-запуска.
Дополнительно пройдены 50 проверок существующего Docker-демо после обновления API.
Результат последнего production-прогона сохранён в
`.tools/release-checks/e249eadc04c04fd1bd1595b124f8fb96/`.

Получение публичного сертификата и работа домена проверяются после размещения
на сервере. Выбор размещения, покупка домена, настройка внешних резервных копий
и решение о переносе прежних данных остаются частью фактического выпуска.
